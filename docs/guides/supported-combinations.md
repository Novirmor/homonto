# Supported combinations

The host × harness × engine combinations homonto supports, and what a
release must show for each before it claims it. `homonto init` generates
exactly these ([ADR 0110](../adr/0110-generate-starting-configurations-in-the-binary.md)),
and the table below is generated from the same declaration
(`internal/starter`), so the two cannot disagree.

A cell is supported in a release only when every evidence key it lists
passed against that release's binaries. A key that was not run is not a
pass. The release notes name the cells a release verified, and the
[release checklist](../release-checklist.md) keeps the evidence.

## Not supported

- **Other harnesses.** Codex and Antigravity have no adapter
  ([harness architecture](../harness-architecture.md)). `homonto init
  --harness codex` is refused before anything is written.
- **Self-managed hosts.** GitLab self-managed and Bitbucket Data Center are
  outside 1.0.
- **External engines and workflows** are supported through the
  [package contract](../contracts/README.md), not generated by `init`.
  Declare them by hand.

## Claude Code limitations

Claude Code runs every engine at the workflow tier, with limitations
accepted per guarantee in
[ADR 0105](../adr/0105-accept-limited-claude-code-capabilities-per-guarantee.md):

- worker shell rules are applied by homonto's policy hook, and a session not
  started as the coordinator agent carries no policy;
- a publication draft holds at most four items (`AskUserQuestion`), and in
  `claude -p` a required decision is reported pending instead of asked;
- publication approval is correlated over a local socket, within the
  honest-agent model;
- a worker's refused permission prompt is inferred, because Claude Code
  reports the prompt but not its answer;
- there is no status panel or idle notification.

`homonto doctor` reports them for each project. See
[Claude Code](claude-code.md#how-guarantees-are-kept).
